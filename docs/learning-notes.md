## 2026-07-16 · 度量层最凶的 bug 不是崩，是面不改色地报一个漂亮的零

**现象**：EVAL-002 是把评测的 9 个指标从 trace 流里**数出来**的度量层。写它的时候，藏着两道最容易
一脚踩进去、且踩进去还不吭声的缝。**缝一，读错了存储。** 招牌安全指标 Human Approval Trigger Rate
要数 `approval_decision` 事件；可这些事件只写进 JSONL，**不进 SQLite 索引**——那个索引（D-023/024）
按设计只收 `tool_call` 一种 kind。度量层要是图省事去查 `Database.tool_calls()`，它**不会报错**，只会
一条 approval 事件都捞不到，把审批触发率算成 `n/a`（0/0）——一个"没有任何高危调用逃过审批"的漂亮
结论，其实是"我压根没在存着审批记录的那口井里打水"。**缝二，比错了常量。** 度量层拿字符串
`"InvalidArgsError"` 去比 payload 里的 `error_type`，而那串是 app 侧 `ErrorType` 这个 StrEnum 的
`.value`；两处之间**没有任何类型级的链子**（度量层在 `eval/`，连 mypy 都不扫它），枚举哪天改个名，
invalid-tool-call 率当场恒等于零，照样一声不响。

**剖析**：两道缝形状不同（一个"读错存储"、一个"比错常量"），可失败形态一模一样，而且都是**度量层
特有的那种最坏形态——静默的零**。一个普通功能读错了存储，多半会崩、会拿到 `None`、下游会炸；而
度量层的天职就是"数数"，数出来是 `0` 或 `n/a` 是**完全合法**的输出形状。于是"管子根本没接通"和
"真的就是零"，在输出上**长得一模一样**——你拿不到任何异常信号来区分它俩。更毒的是零的**方向**：
审批触发率的 `n/a`、invalid 率的 `0.000`，读起来都像"安全、干净、没问题"。所以一个接错了管子的度量
层不是沉默，是**主动撒谎报平安**——它把"我没在量"伪装成了"我量到一切都好"。

**经验**：凡是"把某个东西数出来"的层（metrics、监控、审计报表、eval 计分），它的**特征性 bug 不是
抛异常，是安静地报一个假的干净数**。根子在于：它跨的每一道缝——读哪口存储、比哪个字符串、匹配哪个
kind——**失败时都退化成"什么都没找到"，而"什么都没找到"对一个计数器来说是合法输出**（0 / n/a），
不是错误。两条落地。① **要读就读事实来源**（append-only 的原始事件流），别贪那些"为别的目的裁过一刀"
的投影：一个按 kind 过滤的索引，对它漏掉的那些 kind 的消费者来说是**彻底的盲区，而盲区表现为可信的
零**。这里度量层只 import `TraceEvent`、坚决不碰 `Database`，正是因为 SQLite 是投影、JSONL 才是账本。
② **跨模块的每一处"魔法常量对齐"**（这里 `eval` 的字符串去对 `app` 枚举的 `.value`），都得有一条测试
拿**生产者真吐的输出**去验，而不是两头手写同一个常量——否则它和 2026-07-05 那条"串供 fixture"是同
一个病：测试和被测从同一个假设出发，一起错、一起绿。归总一句：**对一个度量层报出来的"一切正常"，
默认先怀疑管子接没接通，再信那个数**——因为它最擅长的，就是在管子断了的时候面不改色地报平安。这
和前面一整族"静默的跳过能掏空一个你以为还在的保证"是同一母题的又一面：那些讲某个**动作**静默地
漏了（少落一条 trace、悄悄删掉一条引用），这条讲某个**数**静默地空了——而空出来的那个零，恰好把
自己打扮成了好消息。

## 2026-07-14 · 同一道去重门，坐在审批前还是审批后，拦的是两回事

**现象**：给 registry 加 LoopGuard——同一次运行里，同名 + 同参数的**连续重复**调用直接硬拦，免得
agent 在一个失败调用上空转死磕。查重本身不难（存一个 hash、相等就拦），真正定生死的是**这道查重
门插在 dispatch 流水线的第几步**。当时 dispatch 的顺序是 `取工具 → 校验参数 → 审批门 → 执行`。
最自然的插法，是顺着"执行前最后一道保险"的直觉，把查重塞在**审批之后、执行之前**——反正它管的
是"别重复执行"嘛。可这么放，门就废了一半：一个被重复提交的高危调用（比如同一个 apply_patch 的
diff），会**先把人从审批门叫起来**、让人对着同一个 diff 再按一次 `y`，然后才轮到查重说"这是重复，
拦下"。而"别拿同一个调用反复烦审批的人"恰恰是 LoopGuard 存在的头号理由——放在审批后面，它拦住了
"重复执行"，却没拦住"重复烦人"，把自己最该省的那笔开销原样付掉了。

**剖析**：所以查重门必须坐在**审批门前面**（校验之后、审批之前）：一个连续重复的高危调用，既不送
去烦人审、也不执行，只留一条 `LoopBlockedError` 的 trace。位置往前挪一格，还顺带白捡两个好处。其
一，它查的是**校验后**的参数、不是原始入参：两个原始 dict 只要校验成同一个模型（补了默认值、键序
不同），就被正确判成"同一个调用"，查重口径天然是规范化的。其二，非法参数在**校验阶段**就挂了、
根本走不到查重这一步，于是坏参数**永远污染不了**查重历史——历史里只会有"合法过一次"的调用。这三
件事（不烦人、规范化口径、免于坏输入投毒）全是**同一个放置决定**一次性给的，只要门在流水线里的
位置对；错一格，三个好处一起没。

**经验**：一条串起多道检查的流水线里，"某道检查排在第几步"不是实现细节，是**它到底在保护谁、以什么
口径生效**的决定性选择。判据就一句：一个"坏调用"打进来，在**走到这道检查之前**，已经付掉了哪些
代价？LoopGuard 要省的是"惊动人 + 重复变更"这两笔，那它就必须坐在"惊动人"（审批门）和"变更"（执行）
的**上游**；但凡往后挪一格到审批之后，它照样拦得住执行，却已经先把人叫起来了——门还在，可它存在
的头号理由已经落空。这个规律对一整类"挡在昂贵动作前面"的机制都成立：限流、幂等键、去重、缓存，
全都是**坐在它要保护的那个昂贵步骤的前面**才有意义，挪到后面就退化成"记了一笔、但钱照花"。它和
前面两条 fail-closed 的教训是同一族的第三面：那两条一条管**门朝哪个方向偏**（"没配门"不能默默等于
"放行"），一条管**门的前置条件划多宽/卡在什么时机**（太宽会在 happy path 上误拦、撞上自家合法
状态），这条管**门站在流水线的哪一格**——方向对、条件也对，可**位置错一格，门照样形同虚设**。一道门
要真正生效，方向、条件、位置这三样得同时对，缺一样它就悄悄成了摆设。

## 2026-07-14 · fail-closed 的门，最容易在"开太宽"和"撞上自家合法状态"上翻车

**现象**：`git_create_branch` 要保证从一棵"干净的树"上建工作分支——脏树上 `git checkout -b`
会把未提交的改动一起带进新分支，和后面 apply_patch 的改动混成一团。这道"必须干净才放行"的门，
最顺手的两种写法各埋一个坑。**坑一，"脏"的定义开太宽**：把脏定义成 `git status --porcelain`
有任何输出。测试用的临时仓是干净的，这么写全绿。可真实用户的仓库**永远**带一堆未跟踪文件
（构建产物、`.env`、草稿），`--porcelain` 会把它们全列成 `??`，于是这道门在真实仓库上几乎必然
拒绝——而未跟踪文件根本不会被 `checkout` 带进新分支的 tracked diff，压根构不成我要防的那个污染。
**坑二，检查时机撞上系统自家的合法状态**：要求"建/切分支前树必须干净"这条，恰好会被**上一步
自己的成功**违反——apply_patch 打完补丁，树就**故意**变脏了（那正是它该干的）。一旦流水线重入
（resume），git_create_branch 再跑一遍时已经在目标分支上、且树是脏的（刚打的补丁）；一道"无脑
要求干净树"的门会在这里拒绝，把"补丁已打好、正常重入"这条最合法的路堵死。

**剖析**：两个坑都不是"要不要 fail-closed"（该 fail-closed），而是"这道门的**前置条件**划在哪"。
坑一的修法是把"脏"从"任何 porcelain 输出"收紧到"tracked 改动"——`git status --porcelain
--untracked-files=no`，门只对真正会被 checkout 带过分支的已跟踪改动敏感，对每个真实仓库都有的
未跟踪杂物视而不见。坑二的修法是把"已在目标分支 → 空操作成功"这条判断，放在洁净检查**之前**：
当前分支就是目标分支时直接返回 no-op，**根本不看树脏不脏**——因为这一步本就不切换、不携带任何
东西跨分支，脏在这里是合法的（它是上一步成功的产物）；洁净门只在"确实要切/建"那条路上把关。

**经验**："fail-closed 更安全"是对的，但一道 fail-closed 的**前置条件**没划准，它自己就成了新的
失败源，且有两种典型翻法。① **门开得太宽，在正常情况下就拦。** 一道天天在 happy path 上误报的
安全门，结局只有两个——被人 `--force` 绕过，或把所有活堵死；两种都等于没有门，甚至更糟（它还
给了"有防护"的错觉）。所以前置条件要**精确贴着你真正要防的那个危害**（这里：会被 checkout 带过
分支的 tracked 改动），而不是那个"看起来相关、却宽得多"的条件（任何工作区变动）。判据：把这道门
放进真实环境，它会不会在我明明该放行的常见状态上喊停？会——那它开太宽了。② **门的时机，撞上
系统自己造出来的合法状态。** 你加一条 fail-closed 前置（"必须处于状态 X 才能继续"），要多问一句：
系统自己某条成功路径，会不会**恰好**把自己带出 X？这里 apply_patch 的成功＝把树弄脏＝正是洁净门
要拦的状态，两个本该协作的工具，一个的正常产物成了另一个的拒绝理由。修法通常不是放松那道门，而是
**把"合法的重入"识别在前**（先判 no-op、再判洁净），让门只管真正要动手的那条路。这和前面"安全
默认必须是拒绝"正是一枚硬币的两面：那条讲**缺了保护别 fail-open**（没门≠放行），这条讲
**fail-closed 也有它自己的坑**——划得太宽或卡错时机，会在合法状态上 fail-closed，把正常的路也一起
拒了。fail-closed 只定了"默认往哪偏"，没定"拿什么条件来偏"；后者划不准，一道过严的门和一道缺失
的门一样能把系统弄坏，只是坏的方向相反。

## 2026-07-06 · 给模型的输出加校验时，校验器该"标注"而不是"改写"

**现象**：给分析报告接上引用校验——模型给出的 `file:line` 引用和可疑文件路径，运行收尾时拿真实
仓库核一遍。最顺手的冲动是奔着"帮模型把错的擦掉"去：哪条引用指向不存在的行/文件，就把它从报告里
删了，只留干净的，CLI 输出确实清爽。但这么做，系统就成了模型报告的**合著者**——它悄悄改了模型
说过的话；更糟的是，它恰好把"模型爱瞎编引用"这个**最该被测量的失败信号**给擦没了。旁边那套评测
正想问"模型的引用有几成是真的"，可你在收尾处已经把假的删干净，量出来永远是 100%——校验非但没
帮上评测，还把评测的题目给销毁了。

**修复**：校验只**标注**、不**改写**。报告原样保留模型写的引用与可疑文件；另起一个"核验结果"
结构，逐条记 valid / 越界 / 不存在 / 逃逸，挂到运行结果和那条终态事件上，CLI 只在有未核实项时
多打一段告警。"模型声称的"和"代码核实的"两个面并排摆着，交给人和评测去判。关键动作是把核验结果
和模型报告**分开存**——报告是"模型说了什么"，核验是"我验了什么"，绝不揉进同一个结构。

**经验**：凡是在一个"生成器"（模型）上叠一个"校验器"，默认姿势该是 **annotate，而不是 edit/gate**。
一旦校验器动手删改生成器的输出，两件坏事同时发生：① 系统替模型背了书——它吐出来的东西里混进了
系统的手脚，事后再也分不清哪句是模型说的；② 你把最想观测的错误率**就地抹平**了，"静默修正"会把
失败信号连着失败一起吃掉，而这个信号正是你当初加校验的理由。判据很简单：这个"修正"发生之后，
下游还看得见原始的错吗？看不见——那它就不是校验，是篡改。这和前面"记录是事实来源时要 fail loud"
是同一族的另一面：那条讲**记录**失败别静默，这条讲**核验**结果别静默地改掉被核验的对象；共同母
题——一次好心的静默动作，能把一个你以为还在的真相（模型到底说了啥、错了多少）不声不响换掉。

## 2026-07-06 · 当验收标准是"一个跑出来的数字"，先把量尺和测量拆开

**现象**：评测这块的验收标准是"三个种子 issue 里，正确文件进前三 ≥2/3；每条引用都真实存在"。
这是个**跑真模型才量得出、而且带随机性**的数字。可我的验收流程是离线的（ruff / mypy / pytest +
语义核对），根本没法在自己的门里复现一次随机的联网跑分。硬把"≥2/3"写进这张卡的验收，结果就是
它永远过不了——不是代码不对，是这个标准**结构上进不了离线的门**。

**修复**：把交付面沿着一条缝**切成三段**。① **量尺 = 可离线验收的那部分**：种子仓（带真 bug +
故意会失败的测试）、纯打分函数（top-k 命中、引用有效性）、一个最小评测 runner（核心可注入假
client，离线就能单测接线）——这些我用四关全能验死。② **数字 = 拿真 key 单独跑一次**的产物，留档，
不进我的门。③ **调优（优化定位 prompt、要不要加"仓库总览"工具）= 有条件的后续**：先跑 baseline，
没达标才动手。

**经验**：每张卡都得有一个"我能复核"的验收标准；而一个**随机的、联网才出的指标，本身不构成这样
的标准**。碰上这种卡，别把指标硬塞进验收，而要沿着"确定性/可门控"与"随机/需真跑"这条缝把交付
劈开：先造**量尺**（确定、能单测），把"取数"和"据数调优"都留到量尺就位之后。这里还压着一条**先量
再调**：未调的定位逻辑说不定本来就够 ≥2/3——在量尺出现之前就改 prompt、加工具，是在没刻度的秤上
称重，纯凭手感；先把尺子造出来（顺手量第一次），才是 primitive-first 的正解，也逼着自己别做投机式
优化。它和前面那一整族"全绿测试的盲区"不同：那些讲"测了、却没断到点上"，这条更靠前一步——**这个
验收标准根本没法在我的验收环境里跑**，所以要在交付结构上，把"量具"和"读数"当成两件事分开交，
量具求确定、读数求真实。

## 2026-07-06 · 评测固件是"故意坏的代码"，会跟你的每一道质量门为敌

**现象**：给 bug 定位评测造种子仓——一个小 calculator 包，里面**故意**埋三个真 bug（除法符号反
了、百分比漏乘 100、偶数中位数取了上中位），每个 bug 配一条**断言正确行为、于是必然 FAIL** 的
pytest（这样后面"修 bug 让测试转绿"的阶段才有一条红测试可修）。麻烦在于：这堆"该坏的代码 + 该
失败的测试"一进仓库，项目自己的三道质量门会争先恐后地"帮忙"：根 `pytest` 会把那三条注定失败的
测试收进主套件、当场把绿测跑红；`ruff` 会去 lint 那些故意写丑的 bug 代码；`mypy` 也可能顺手去查。
你越想让固件"真实地坏"，它越会污染你那条"必须全绿"的红线。

**修复**：让固件对三道门**各自隐身，且各因不同的理由**——`pytest` 用 `testpaths` 把收集范围钉死
在 `tests/`（固件在 `eval/fixtures/` 下，天然不被收集）；`mypy` 用 `packages=["app"]` 把类型检查
限定在产品代码（固件在外）；`ruff` 单独加一条 `extend-exclude`（**这条最容易漏**：前两道是"范围
恰好没覆盖到"，而 `ruff .` 是**主动扫全仓**的，不显式排除就一定撞上）。三道缺一，`pytest -q` 或
`ruff` 就红。验收时我还**单独**进固件目录跑了一次它自己的 pytest，确认那三个 bug 如期 FAIL——
"固件真的坏"和"固件不污染主门"是两件必须分别确认的事。

**经验**：一旦你的测试资产里出现了"**本该是坏的**"代码（评测固件、负样本仓、演示反例），它就和你
日常"必须全过"的每一道自动化门形成了结构性对立——每道门的默认使命都是"发现坏东西并报警"，而这
堆坏东西是你**故意**摆的。所以得为它逐门下一条**豁免**，而且别想当然"一道门排除了，别的门也排除
了"：`pytest` 靠 `testpaths`、`mypy` 靠 package 范围、`ruff` 靠全扫 `.`，三者的覆盖边界各不相同，
豁免要一门一门单独下。反过来还有一条对偶：固件"真的坏"必须靠一次**独立于主门**的运行来证明（单独
跑它自己的测试、看它 FAIL），否则你只知道"它没吵到主门"，并不知道"它到底坏没坏"。这和前面
".gitignore 会悄悄吃掉固件"是同一族——那条讲固件被忽略规则**误删**，这条讲固件被质量门**误抓**；
共同点是：精心摆好的测试资产，跟那些"按模式一刀切"的仓库级机制（ignore 规则、lint/type/test 的
收集范围）天生会打架，入库前得逐条确认它们各自把固件当成了你想要的那个角色。

## 2026-07-05 · 三个同门角色，循环 bug 只落在那个"不得不改写骨架"的身上

**现象**：Planner / Executor / Critic 是一套三兄弟，共享同一个"结构化输出 + ≤2 修复"的角色形状。
可它们的验收结局很不一样：Planner 有个小坑（refusal 不落 trace），Executor 有个真坑（`while
True` 里 `pause_turn`/空 tool_use 无界空转），而 Critic 一次过、零返工。一开始我以为是 Critic 写得
更仔细，复盘才看清：**Critic 根本没重新证明"会终止"这件事——它是把 Planner 那个 `while attempts <
max_attempts` 的骨架整段照抄过来的**。Planner 和 Critic 都是纯推理角色，不带工具，于是每一轮循环
都无条件 `attempts += 1`，无论模型返回什么 stop_reason 都被 `max_attempts` 兜住——终止性是**跟着
这个控制骨架一起被继承下来的，白拿的**。Executor 偏偏没法照抄：它要在循环里穿插工具派发，只能
另起炉灶写成 `while True` + 按分支设界——而一旦把"计数器封顶"改写成"逐分支封顶"，`pause_turn`
和空 tool_use 那两条分支就被漏掉了。**同一个终止不变量，抄下来的地方稳如泰山，重推的地方悄悄漏
了。**

**剖析**：`while i < N` 是一种 **categorical（无差别）的界**——它成立与哪条分支执行无关，甚至与
"将来会不会加新分支"无关，只要循环体每轮推进计数器，界就永远在。这种"对所有分支（含未来的分支）
都成立"的鲁棒性，正是它的全部价值。可当需求逼你把它拆成"按 stop_reason 分派"的循环时，这条无差
别的界就**碎成了每条分支各自的界**：现在每一个 `case` 都得自带一个推进量，漏掉任何一个（哪怕是
`pause_turn` 这种看着人畜无害的），就是一个隐形的无界洞——而且编译器、类型检查、happy-path 测试
全都看不见它。所以这类 bug 有个很强的规律：**它们扎堆出现在"被迫偏离模板"的那个点上**，而不是均匀
散布。Planner→Critic 是照抄，安全；Planner→Executor 是被工具循环逼着改写，坑就落在改写处。

**经验**：两条落地。① **能照抄的控制骨架就别"改写成等价的"**——当一个新组件在结构上和某个已被验证
过的兄弟同形，就把它的整段控制骨架原样搬过来，而不是"照着意思重写一个等价循环"。不变量是随骨架
继承的，改写（哪怕自认为等价）就是把这份免费的保证亲手放掉。② **真正危险的是那些"照抄不了、必须
另起炉灶"的点**——新需求（这里是工具穿插）逼你离开模板的地方，就是该拉响警报的高风险工地：在那里
必须把不变量**显式重新证一遍**（补一段独立的终止性论证 + 喂一个对抗输入的测试），因为你刚刚交出了
模板白给的那份担保。这条和上一条"要证明有界就得喂个存心不停的输入"是同一枚硬币的两面：那条说
"终止性证不了于一堆乖样本"，这条补上"——而你最不需要重证的地方，恰恰是照抄了有界骨架的地方；对抗
输入的火力，该集中打在你被迫改写循环的那几个点上"。

## 2026-07-05 · 要证明循环"有界"，得喂它一个存心不肯停的输入

**现象**：验收 Executor 时逮到一条藏得很深的：它的主循环从 P2 模板的 `while steps < max_steps`
（每轮无条件自增、无论模型返回什么都终止）被改成了 `while True`，只对 `tool_use`（`tool_calls`
自增，有界）和 `end_turn`（`output_attempts` 自增，有界）两条分支设了界。可 `pause_turn` 那条只
把消息追加进去、**不增任何计数**；`tool_use` 携带**空** `tool_calls` 列表时 for 循环空转、也**不
增**。于是只要模型一直返回 `pause_turn`（或空 tool_use），循环就永久空转——一个"有界"角色最该
守的终止保证被悄悄拆了，还正好违背项目那条"预算在代码里强制、永不信任模型自停"的信条。七条单
测全绿：因为**每条脚本喂进去的 response 列表都是有限的、自己会走到 end_turn 的**。没有任何一条测
试喂一个"存心不停"的模型，所以这套绿测证明的是"这些乖脚本会停"，而**根本没碰**"所有输入都会
停"这个真正要验的性质。

**修复**：加一道代码级上限——连续"无进展"的 completion（既没派工具、也没尝试综合）计数，越过
`_MAX_STALLED_COMPLETIONS` 就 soft 返回 `incomplete` + 落 `tool_result`（`reason=
stalled_without_progress`），任何一次真派工具或真综合都把它清零。再补一条回归测试：脚本喂一个
"永远 pause_turn"的模型，断言它照样在有限步内终止、并落了那条事件——把"存心不停"的对抗输入
第一次真正喂进去。

**经验**：**终止性（以及任何"对全体输入成立"的性质：有界、幂等、压力下 fail-closed、不无限重试）
证不了于一组'碰巧会停'的样本**。前四面（漏了断言 / 走错了门 / 喂错了料 / 断言了缺席）的输入至少
都**触发到了**要验的行为，错在断错、进错门、或串供；这条更靠前一步——**要破坏性质的那类输入压根
不在语料里**。你拿一百个会自己收敛的输入去跑，跑得再绿也只是把"存在性"（这些能停）误当成了
"全称性"（都会停）。有一个特别可靠的代码气味能提前嗅到它：**当一个循环的终止依赖"响应的形状"
（这里是 `stop_reason`）、而不是一个每轮无条件自增的计数器时**——也就是有人把 `while i < N` 这种
categorical 的界，换成了挂在若干分支上的 conditional 的界——几乎必有一条没被界住的分支。落地
一条：凡交付带"有界 / 会终止 / 有上限"承诺的东西，验收清单里必须有一条**对抗测试**，专门喂那个
"如果没人拦它就会跑到天荒地老"的输入，断言代码自己把它拦下了；happy 脚本全绿是必要条件，不是
充分条件。

## 2026-07-05 · 断言"什么都没发生"的测试，会把一个本该发生的遗漏钉成规范

**现象**：验收 Planner 时逮到一条：模型 refusal（拒答）那条分支直接抛错走人，**一条 trace 事件
都没落**——可 planner 明明跑了、token 都花了、还是终态失败，trace 里却一片空白；而旁边"修复
耗尽"那条终态失败分支是**落** `error` 事件的。两条终态失败一个记一个不记，本就不对。更要命的是
那条**测试**：它断言 `store.read(run_id) == []`——把"refusal 不产生任何 trace"当成**正确行为
钉死了**。于是这个 trace-first 的洞不是"没测到"，是"测到了、还盖了章"：后来人看见这条绿测试，
会以为"refusal 本来就该静默"。

**修复**：让 refusal 分支和"修复耗尽"对称——落一条 `error` 事件（reason=refusal，带
usage/latency）再抛。测试翻正：从"断言什么都没有"改成"断言落了一条 error 事件"。

**经验**：一个本该有副作用的操作（该落日志、该发事件、该写审计、该记账），"**忘了做**"和
"**故意不做**"，在测试眼里长得**一模一样**——都是"什么都没发生"。所以 `assert x == []`、
`assert_not_called()` 这类**断言"缺席"**的测试天生是弱证据：它分不清"正确地什么都没干"和"有人
忘了那一下"。更阴的是它还是个**反向承诺**——不只是没防住，它主动把"没发生"写成了规范，把 bug
盖章成 feature。落地一条：凡要断言"某操作没产出、没被调用"，先停一秒问自己——这个"没有"，是我
想要的静默，还是一个被我顺手确认掉的遗漏？尤其当同一个操作在**别的分支是有副作用的**（这里
refusal vs 修复耗尽），不对称本身就是信号。这和前面"漏了断言""走错了门""喂错了料"是同一族的第
四面：那三条错在**没测到点**，这条错在**把不该测绿的测绿了**——断言的方向反了。

## 2026-07-05 · 拿被测代码"照着搓"出来的 fixture，测试和代码就成了串供的两个证人

**现象**：验收 SQLite 索引那张卡，`tool_calls` 索引的单测全绿——手造几条 trace 事件喂进
`index_events`，断言索引出来的行字段都对。但这些事件的 payload，是测试里一个帮手函数**照着
`index_events` 要读的形状**手搓的。真实系统里这些事件不是手写的：是 `RegistryTraceSink` 把
`ToolTraceRecord` 翻译出来、写进 JSONL、再读回来的——中间有一跳最容易错：`error_type` 是个
enum，sink 写进 payload 的是它的 `.value`（字符串）。手搓的 fixture 恰好也填了字符串，于是
"生产者写的形状 vs 消费者读的形状"这道缝，从没被真正对上过。测试绿只证明了"我手喂的消费者
能读"，没证明"生产者真吐的消费者能读"。万一两头我都想错了（都以为是字符串、其实 sink 漏了
`.value` 直接塞 enum），测试照样绿——fixture 和代码是同一个脑子出来的，错得一模一样。

**修复**：补一条组合测试，不再手搓中间产物——真走 `RegistryTraceSink(store).append(record) →
store.read(run_id) → index_events(...)`，让**真实生产者**去生成那批事件、再断言索引结果。sink
的 `.value` 那一跳、JSONL 序列化往返、消费者解析，三段端到端焊住，任一段偷改契约这条就红。
关键不在"多一个测试"，在于把测试输入从"照着消费者手写的常量"换成"生产者真产的东西"。

**经验**：一个测试要能证伪代码，输入和被测代码得是**两个独立的证人**；可一旦 fixture 是你照着
被测代码的期望手搓的，俩就串供了——同一个作者、同一个假设，永不互相矛盾，"全绿"于是退化成
"我跟我自己一致"。这在**两个分开开发的模块之间的隐式契约**上最致命：生产者写什么形状、消费者
读什么形状，只有让消费者去吃生产者**真吐的**输出，那道缝才验得到；拿手搓替身喂消费者，测的是
替身、不是契约。落地一条：凡跨模块的数据缝（A 写、B 读），至少留一条测试让 B 吃 A 的真实产物，
而不是两头都喂手写常量。这和"全绿也能盖住没断言的不变量""测试从后门进、用户从前门进"是同一族
的第三面——那两条是**漏了断言**和**走错了门**，这条是**喂错了料**：料是照着答案配的，自然尝不
出错。

## 2026-07-05 · 当"日志"其实是事实来源，"别让埋点拖垮主流程"这条常识要反过来

**现象**：给 trace store 收尾时，有件容易顺手做错的事：dispatch 每次工具调用后往 trace sink 写
一条事件，万一这条写入抛异常怎么办？几乎所有人的第一反应——连同"生产环境别让日志/埋点把主
流程搞崩"这条根深蒂固的工程常识——都会说：包进 try/except，吞掉，接着跑，日志坏了不该拖累正
事。但 RepoPilot 的 trace 不是旁路：JSONL 是这次运行的**唯一事实来源**（SQLite 只是它的索引，
D-023）。在这儿吞掉一次写入失败，产出的不是"少一行日志"，而是"一条自称完整、其实缺页的运行
史"——下游 replay、审计、eval 全在一份连自己残缺都不知道的记录上做判断。

**修复**：让 sink 的异常**直接往上抛**（D-012 早定了这条，这次补红线测试钉死它）。落到代码里是
个反直觉的位置：registry 里"追加 trace"那句必须待在 dispatch 的 try/except **之外**——正因为在
外面，它的异常才不会被"把工具异常翻译成 ToolError"那套逻辑顺手接住吞掉。测试注册一个"一写就
炸"的假 sink，断言 `dispatch` 把 RuntimeError 原样抛穿。这行没被 try 包住的 append 看着特别像
个 bug，而最该防的恰恰是将来某个"好心人"（也包括我自己）把它挪进 try 里"顺手加固"——那一挪，
红线就被悄悄拆了。

**经验**："别让埋点拖垮主流程"没错，前提是它真是旁路埋点。一旦某份记录被提升成**事实来源**
（trace-first、event sourcing、账本），它的写入失败就不再是"少记一笔"，而是"事实本身错了"，这时
必须 fail loud、让它炸，而不是 fail silent。判据很简单：这条写入要是丢了，别处还留着同一个事实
吗？没有——那它就不是日志，是数据，得按数据的可靠性来待它。这跟前面"安全默认必须拒绝"（缺了门
就停、别放行）是同一族的两面：那条讲**授权**缺失时别默默放行，这条讲**记录**失败时别默默继续；
共同的母题——一次静默的跳过，能不声不响地掏空一个你以为还在的保证。

## 2026-07-05 · 测试和真实用户，往往从不同的门进入你的程序

**现象**：给 CLI 写完 Typer 命令和一整套 CliRunner 测试，全绿。但 CliRunner 是直接
`import app.cli` 再调 `app()`——它从"Python 函数"这道门进来。真实用户敲的 `repopilot ask …` 却是
从另一道门进来的：`pyproject` 里 `[project.scripts] repopilot = "app.cli:main"` 这行声明式配置，
由安装器生成一个控制台脚本，去 import 那个模块路径、调那个函数名。这行配置里任何一处笔误（模块
路径、函数名、甚至 `main` 压根没定义），CliRunner 测试一个都发现不了——因为它根本不走这条路。
测试全绿，装出来的命令却可能一敲就 ImportError。

**修复**：验收时额外跑一次 `uv run repopilot --help`，确认控制台入口真能解析到 `main`、子命令与
参数都在。也就是至少让程序从"真实入口"冷启动走一遍，哪怕只是 `--help` 这种不触网、不干活的冒烟。

**经验**：凡是"声明式的入口/部署配置"——`entry_points` / `[project.scripts]`、Dockerfile 的
`CMD`、systemd unit、cron 行、CI 的启动命令——都有个共性：进程内的测试框架结构性地够不着它们，
它们只在"真的那样启动一次"时才被验证。这和前一条"全绿也能盖住没断言的不变量"是姊妹，但落点不
同：那条讲的是**你断言了什么**，这条讲的是**你从哪道门进去**——测试从后门进、用户从前门进，前门
那把锁没人试过。所以凡交付带"入口"的东西（CLI、服务、容器），验收清单里都该有一条"从真实入口
冷启动一次"。

## 2026-07-05 · 全绿的行为测试，照样能盖住一个没人断言的不变量

**现象**：给单轮工具回路做验收，131 条测试全绿——答案、状态、工具调用记录、usage 累加，每项
输出都对。但复核代码时发现回路给每个 tool_use step 都现生成一个新 run_id（`uuid4()` 写在循环
里）。run_id 本该是"一次运行"的关联主键，每步一换意味着同一次提问里 step1 的 search 和 step2 的
read 会落到两个不同 run_id 下——等 P3 的 trace store 上线，一次运行的调用就再也拼不回一条时间
线。测试为什么全过？因为 P2 里 run_id 还没有任何下游消费者，它不影响任何被断言的输出；而所有
测试断的都是"行为/输出"，没有一条去断"同一次运行的所有 dispatch 共享同一个 run_id"这个不变量。

**修复**：把 run_id 提到循环外一次生成、全程复用同一个 ToolContext（两行 hoist），131 条测试原样
全绿——恰好反证这个 bug 从来不在任何被观测的输出上。并把"补一条 run_id 一致性断言"明确记进下一
张卡。追到源头，坑其实埋在交底卡的措辞里：我写的是"每轮生成一个 run_id"，"每轮"在中文里既能读成
"每次运行"又能读成"每次循环迭代"，实现方忠实照着后一种做了。

**经验**："测试全绿"证明的是"被断言的那些行为成立"，不等于"该有的不变量成立"。最阴的 bug 是那种
当前不影响任何输出、要等后续阶段才引爆的——它天然躲开一切只看输出的测试。两条落地：① 凡是跨
调用/跨步骤需要保持一致的东西（run_id、事务边界、幂等键），就该有一条专门断言这个"一致性"本身的
测试，而不是指望被行为测试顺带覆盖；② 用自然语言写规格时，凡有"每…"这种量词，先追问一句"每
什么"——中文的"每轮"、英文的"per round"都是二义的，规格里一个模糊量词能一路变成实现里一个 latent
bug。这和"被 skip 的测试等于没测"是同一母题：绿灯只覆盖它照到的地方，而覆盖的洞可以是黄的
（skip），也可以是绿的（跑了、但没断到点上）。

## 2026-07-05 · 拿输入去"抢救"结构时，最该先写的是假阳性那条红线

**现象**：给 LLM adapter 加"纯文本工具调用抢救"——模型偶尔把 tool call 以纯文本塞进 `content`
而不是结构化字段，adapter 得把它认出来、还原成结构化调用。第一版最自然的写法是奔着"能不能认
出来"去：content 里有没有 `{"name":..., "arguments":...}` 这种形状，有就抢救。但这个方向天生
危险：真正会出事的不是"该抢救的没抢救"（大不了让模型重说一遍），而是"把不该抢救的抢救了"——
一段正常散文答复里恰好举了个工具调用的 JSON 例子、或者模型在解释"我打算调用 read_file"，都
可能被误判成一次真实调用，于是凭空造出一个工具调用送进 dispatch。抢救逻辑一旦有假阳性，就等于
让模型的散文能悄悄驱动工具执行。

**修复**：把判断从"像不像"收紧成"是不是整体就是"——content 去空白、剥掉至多一层围栏/标签后，
必须**整串**恰好是工具调用 JSON（用 `json.loads` 解整串，散文包着 JSON 会直接解析失败），且键集
**恰好**是 `{name, arguments}`，多一个键都拒；再加一道前置门：只有本次确实提供了 tools、且结构化
字段为空时才尝试。最关键的是测试顺序：先把最像的假阳性写成红线用例——"散文内嵌工具调用 JSON →
绝不抢救""多一个 extra 键 → 不抢救""没提供 tools → 不抢救"——再写正向的三种命中形态。护栏是被
这几条反向用例定义出来的，而不是 happy path 顺带带出来的。

**经验**：凡是拿"输入"（用户的、模型的）去匹配某个模式、并据此触发副作用的地方，风险几乎总在
假阳性一侧，而非假阴性。假阴性通常只是"没帮上忙"，假阳性却是"帮了倒忙，还是悄悄地"。所以这类
逻辑的测试要倒过来写：先钉死"什么绝对不能命中"，正向命中反而是次要的。这和前面 glob 过滤那条
"模式也是一种输入、也要过安全审查"是同一族——凡是外部能塞进来的东西，默认都往"它会不会指到、
触发到我不想让它碰的东西"那个方向去设想，并把那个最坏设想先变成一条红色测试。

## 2026-07-04 · 实现 glob 过滤：两条看起来现成的路，其实都有坑

**现象**：给代码搜索加 glob 过滤（`**/*.py` 这种），第一反应是拿标准库里现成的东西套。但两条
最顺手的路都不对：`fnmatch` 把 `*` 翻译成"匹配任意字符、连 `/` 也一起吃"，于是 `src/*.py` 会把
`src/a/b/c.py` 也算进来——它根本不认目录分隔符，`**` 和 `*` 在它眼里是一回事。换 `PurePath.match`
呢？它认目录，但对递归 `**` 的支持要到 3.13 的 `full_match` 才有；在项目下限 3.12 上，
`PurePosixPath("foo.py").match("**/*.py")` 会因为"模式段数比路径段数多"而**匹配不到顶层文件**。
两条路各自在不同的方向上错，而且都是那种单测一两个用例还发现不了的错。

**修复**：绕开字符串匹配，改用 `root.glob(pattern)` 让 pathlib 自己算出匹配集合（`**` 的递归语义
它原生就对），再和"安全遍历"得到的文件集合取交集——遍历那一层仍独占隐藏/软链/二进制的过滤权。
另外把 `..`、绝对路径、盘符前缀的 glob 直接拒掉：过滤器不能顺手变成第二条越狱通道。测试里专门
钉两个反向用例：`*.md` 只能回顶层、`**/*.py` 必须递归——正好各自证伪上面两条歧路。

**经验**：标准库给了名字相似的工具（fnmatch / match / glob / full_match），但它们对"路径分隔符"
和"递归"的语义各不相同，"看起来能用"和"语义正确"之间隔着好几个边界用例。选之前先把最刁的两个
用例（跨目录、顶层文件）写下来拿每个候选比一遍，比事后调试便宜得多。还有：凡是让用户传模式串去
筛文件的地方，都要先问一句"这个模式能不能指到工作区外"——glob 也是一种输入，也要过安全审查。

## 2026-07-04 · .gitignore 会悄悄吃掉和运行时产物同名的测试固件

**现象**：给工具测试造了一个内容确定的迷你仓库当固件，里面故意放了 `.cache/pip.log` 和
`data/long_file.txt` 来测隐藏文件和长文本。本地跑测试全绿——因为测试直接读磁盘上的源目录，
文件都在。但仓库根的 `.gitignore` 里，为屏蔽运行时产物写了 `data/` 和 `*.log` 两条规则，它们
不认路径前缀，照样命中固件里这两个文件。结果就是：`git add tests/fixtures` 会把它俩默默跳过，
提交上去的固件是残缺的——本地绿、别人 clone 下来缺文件、CI 里才炸。

**修复**：暂存前先用 `git status --ignored` / `git check-ignore -v` 把固件清单里每个文件过一遍，
确认没有被忽略规则命中的漏网；对确实被广义规则挡住、但又必须入库的固件文件，用 `git add -f`
显式强加。并在测试里用文件清单做合同断言，这样"少提交了一个文件"会立刻变成一条红色测试。

**经验**：`.gitignore` 是按模式匹配的，它不区分"这是运行时垃圾"还是"这是我精心摆好的固件"——
只要路径撞上模式就一视同仁地忽略。危险在于本地测试读的是工作区磁盘，看不见 git 这层过滤，
于是"文件存在"和"文件入库"是两件事，而绿灯只证明了前者。凡是往仓库里放和忽略规则可能重叠的
资产（固件、示例数据），都要单独确认它真的被追踪了，而不是假设 add 了就进去了。

## 2026-07-04 · 安全默认必须是"拒绝"——"没配门"不能等于"放行"

**现象**：给调度层写审批门时，最顺手的写法是"如果有门、且门拒绝，就拦下；否则放行"。但这里
藏着一个洞：当一个高危工具（比如日后的 apply_patch）在一个还没接上审批门的环境里被调用——
此时门是 `None`——上面这套逻辑会让它一路畅通地执行下去。也就是说，"忘了接门"被代码默默
翻译成了"这次不需要审批"。整个"人在回路"的安全承诺，可能因为一个 `None` 就悄无声息地失效。

**修复**：把判断顺序倒过来，先看风险等级。只要是 high risk，门是 `None` 就直接 fail closed，
返回一个 `ApprovalDeniedError`（"no approval gate configured"），工具函数一次都不执行。门的
"存在"本身成了执行的前置条件，而不是"存在并且同意"。另外单独写了一条测试钉死它：注册一个
高危工具、不给门、断言工具函数从头到尾没被调用过。

**经验**：安全机制的默认值必须偏向拒绝（fail closed），而不是偏向可用（fail open）。判断
"某个东西缺失"的时候尤其危险——缺配置、缺门、缺 token，代码很容易顺手把它当成"那就跳过这一步"，
而在安全语境里，"跳过检查"就等于"关掉保护"。规则很简单：保护的存在应当是操作的前提，缺了就停，
而不是缺了就放。

## 2026-07-04 · 被 skip 的测试等于没测——尤其它守着安全边界

**现象**：路径牢笼（path jail）有两层防线，词法层拦字面逃逸（`../`、`C:\`），物理层靠
`resolve()` + 包含判断拦符号链接逃逸。两个 symlink 测试在我这台 Windows 上直接 skip 掉了：
非开发者模式没有创建符号链接的权限（WinError 1314）。也就是说——物理层这层防线，在主开发机上
一次都没真正跑过，`26 passed, 2 skipped` 看着很绿，但绿的那部分恰好绕开了最该验的地方。

**修复**：验收时没让这个 skip 蒙混过去。改用目录 junction（`cmd /c mklink /J`）做带外验证：
junction 不需要特权就能建，而 `Path.resolve()` 跟随它的方式和符号链接一模一样。在牢笼里建一个
指向牢笼外的 junction，再调 `jail.resolve("escape/secret.txt")`，确认它如期抛出
`PathJailViolation`——物理层这才算在本机被实测拦截过，而不是"跳过并祈祷"。

**经验**：`skipped` 不是中性的，它是一个测试覆盖的洞，只是被标成了黄色而不是红色。当被跳过的
恰好是安全关键路径，就得再找一个等价、且不触发那道权限门槛的手段补上——这里 junction 和
symlink 在 `resolve()` 眼里等价，就成了免特权的替身。验收的职责是确认行为，不是确认测试跑了几个。

## 2026-07-04 · pip 和 uv 装出来的是两个世界

**现象**：本地 `.venv` 最早是用 pip 建的，装到的版本贴着 pyproject 的下限走：ruff 0.5、
mypy 1.10、pytest 8。后来切到 `uv sync`，同一份 pyproject，解析出来的却是 ruff 0.15、
mypy 2.1、pytest 9——前后差出大半年的版本，而在此之前所有"检查通过"都是在旧版本上跑的。

**修复**：先在干净克隆上 `uv sync` 重跑全套检查（ruff / format / pytest / mypy），确认新版本下
仍然全绿，再把 `uv.lock` 提交进仓库，把环境钉死。

**经验**：`>=` 约束声明的是"能接受什么"，不是"实际用的是什么"；同一份依赖声明，两次安装可以
得到完全不同的环境。lockfile 应该跟第一行代码一起入库，而不是等出问题再补。另外，验证要在
干净克隆里做——本机 `.venv` 的状态不可信。

## 2026-07-04 · env_prefix 会安静地吞掉不带前缀的环境变量

**现象**：配置项大多带 `REPOPILOT_` 前缀，但 `OPENAI_API_KEY`、`OPENAI_BASE_URL`、
`ANTHROPIC_API_KEY` 沿用行业惯例名，不带前缀。pydantic-settings 配了
`env_prefix="REPOPILOT_"` 之后，这三个变量会被直接无视——不报错、不警告。结果就是：用户明明
`export` 了 key，程序却坚持说缺 key。

**修复**：这三个字段单独用 `Field(validation_alias="OPENAI_API_KEY")` 显式绑定完整变量名
（`validation_alias` 不参与前缀拼接），并为别名字段单独写了测试断言。

**经验**：最危险的配置错误是"不报错的那种"。写配置加载器之前，把 `.env` 契约里所有不规则处
（这里是前缀不统一）逐条列出来写进任务说明，比依赖实现时的直觉可靠得多。
