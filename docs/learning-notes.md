## 2026-07-04 · .gitignore 会悄悄吃掉和运行时产物同名的测试固件

**现象**：给工具测试造了一个内容确定的迷你仓库当固件，里面故意放了 `.cache/pip.log` 和
`data/long_file.txt` 来测隐藏文件和长文本。本地跑测试全绿——因为测试直接读磁盘上的源目录，
文件都在。但仓库根的 `.gitignore` 里，为屏蔽运行时产物写了 `data/` 和 `*.log` 两条规则，它们
不认路径前缀，照样命中固件里这两个文件。结果就是：`git add tests/fixtures` 会把它俩默默跳过，
提交上去的固件是残缺的——本地绿、别人 clone 下来缺文件、CI 里才炸。

**修复**：暂存前先用 `git status --ignored` / `git check-ignore -v` 把固件清单里每个文件过一遍，
确认没有被忽略规则命中的漏网；对确实被广义规则挡住、但又必须入库的固件文件，用 `git add -f`
显式强加。并在测试里用文件清单做合同断言，这样"少提交了一个文件"会立刻变成一条红色测试。

**经验**：`.gitignore` 是按模式匹配的，它不区分"这是运行时垃圾"还是"这是我精心摆好的固件"——
只要路径撞上模式就一视同仁地忽略。危险在于本地测试读的是工作区磁盘，看不见 git 这层过滤，
于是"文件存在"和"文件入库"是两件事，而绿灯只证明了前者。凡是往仓库里放和忽略规则可能重叠的
资产（固件、示例数据），都要单独确认它真的被追踪了，而不是假设 add 了就进去了。

## 2026-07-04 · 安全默认必须是"拒绝"——"没配门"不能等于"放行"

**现象**：给调度层写审批门时，最顺手的写法是"如果有门、且门拒绝，就拦下；否则放行"。但这里
藏着一个洞：当一个高危工具（比如日后的 apply_patch）在一个还没接上审批门的环境里被调用——
此时门是 `None`——上面这套逻辑会让它一路畅通地执行下去。也就是说，"忘了接门"被代码默默
翻译成了"这次不需要审批"。整个"人在回路"的安全承诺，可能因为一个 `None` 就悄无声息地失效。

**修复**：把判断顺序倒过来，先看风险等级。只要是 high risk，门是 `None` 就直接 fail closed，
返回一个 `ApprovalDeniedError`（"no approval gate configured"），工具函数一次都不执行。门的
"存在"本身成了执行的前置条件，而不是"存在并且同意"。另外单独写了一条测试钉死它：注册一个
高危工具、不给门、断言工具函数从头到尾没被调用过。

**经验**：安全机制的默认值必须偏向拒绝（fail closed），而不是偏向可用（fail open）。判断
"某个东西缺失"的时候尤其危险——缺配置、缺门、缺 token，代码很容易顺手把它当成"那就跳过这一步"，
而在安全语境里，"跳过检查"就等于"关掉保护"。规则很简单：保护的存在应当是操作的前提，缺了就停，
而不是缺了就放。

## 2026-07-04 · 被 skip 的测试等于没测——尤其它守着安全边界

**现象**：路径牢笼（path jail）有两层防线，词法层拦字面逃逸（`../`、`C:\`），物理层靠
`resolve()` + 包含判断拦符号链接逃逸。两个 symlink 测试在我这台 Windows 上直接 skip 掉了：
非开发者模式没有创建符号链接的权限（WinError 1314）。也就是说——物理层这层防线，在主开发机上
一次都没真正跑过，`26 passed, 2 skipped` 看着很绿，但绿的那部分恰好绕开了最该验的地方。

**修复**：验收时没让这个 skip 蒙混过去。改用目录 junction（`cmd /c mklink /J`）做带外验证：
junction 不需要特权就能建，而 `Path.resolve()` 跟随它的方式和符号链接一模一样。在牢笼里建一个
指向牢笼外的 junction，再调 `jail.resolve("escape/secret.txt")`，确认它如期抛出
`PathJailViolation`——物理层这才算在本机被实测拦截过，而不是"跳过并祈祷"。

**经验**：`skipped` 不是中性的，它是一个测试覆盖的洞，只是被标成了黄色而不是红色。当被跳过的
恰好是安全关键路径，就得再找一个等价、且不触发那道权限门槛的手段补上——这里 junction 和
symlink 在 `resolve()` 眼里等价，就成了免特权的替身。验收的职责是确认行为，不是确认测试跑了几个。

## 2026-07-04 · pip 和 uv 装出来的是两个世界

**现象**：本地 `.venv` 最早是用 pip 建的，装到的版本贴着 pyproject 的下限走：ruff 0.5、
mypy 1.10、pytest 8。后来切到 `uv sync`，同一份 pyproject，解析出来的却是 ruff 0.15、
mypy 2.1、pytest 9——前后差出大半年的版本，而在此之前所有"检查通过"都是在旧版本上跑的。

**修复**：先在干净克隆上 `uv sync` 重跑全套检查（ruff / format / pytest / mypy），确认新版本下
仍然全绿，再把 `uv.lock` 提交进仓库，把环境钉死。

**经验**：`>=` 约束声明的是"能接受什么"，不是"实际用的是什么"；同一份依赖声明，两次安装可以
得到完全不同的环境。lockfile 应该跟第一行代码一起入库，而不是等出问题再补。另外，验证要在
干净克隆里做——本机 `.venv` 的状态不可信。

## 2026-07-04 · env_prefix 会安静地吞掉不带前缀的环境变量

**现象**：配置项大多带 `REPOPILOT_` 前缀，但 `OPENAI_API_KEY`、`OPENAI_BASE_URL`、
`ANTHROPIC_API_KEY` 沿用行业惯例名，不带前缀。pydantic-settings 配了
`env_prefix="REPOPILOT_"` 之后，这三个变量会被直接无视——不报错、不警告。结果就是：用户明明
`export` 了 key，程序却坚持说缺 key。

**修复**：这三个字段单独用 `Field(validation_alias="OPENAI_API_KEY")` 显式绑定完整变量名
（`validation_alias` 不参与前缀拼接），并为别名字段单独写了测试断言。

**经验**：最危险的配置错误是"不报错的那种"。写配置加载器之前，把 `.env` 契约里所有不规则处
（这里是前缀不统一）逐条列出来写进任务说明，比依赖实现时的直觉可靠得多。

## 2026-07-03 · 选型时先翻 issue 区，再看功能列表

**现象**：确定用 deepseek-v4-pro 之前翻了一圈相关 issue，发现一个已知问题
（DeepSeek-V3 #1244）：tool call 偶尔不走结构化的 `tool_calls` 字段，而是以纯文本形式混在
`content` 里返回。官方文档只会告诉你"支持 function calling"。

**修复**（预案，尚未实装）：直接写进设计——adapter 层负责检测 `content` 里的工具调用形态，
重解析或要求模型重发；Phase 2 加一个 contract test 长期盯住这个行为。

**经验**："支持某功能"和"该功能可靠"是两回事。选型阶段花半小时读 issue tracker，比上线后
debug 半天便宜；发现的坑当场变成设计约束，而不是留给未来的自己。
